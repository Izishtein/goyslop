## Как пользоваться

- **Очередь отсортирована**: § 1 — то, что можно делать прямо сейчас, § 2 — то, что упирается в решение владельца проекта, § 3 — опциональные системы «по запросу», § 4 — то, что заблокировано отсутствием источника.
- **Одна задача = одна пачка = один коммит.** Так шла работа до сих пор, и порядок внутри пачки везде один: разбор книги → данные + тест на данные → схема (`.default(...)`) → UI → проверка в реальном браузере (включая печать) → доки → запись в `state.md` → коммит.
- **Оценка объёма** дана в пачках, а не в часах: «1 пачка» — это примерно как секция Techniques/Spellsongs или каталог фитов, то есть один заход целиком.
- **Источник данных — английские PDF в `files/`.** Русский свод данных (`.docx` там же) — перекрёстная проверка и указатель пропусков, но не первоисточник: он датирован 2025 годом, часть файлов помечена «в процессе перевода», и одно расхождение уже нашлось (Boar Rush: MP12 в книге против MP13 в переводе). При конфликте выигрывает книга, расхождение записывается в `state.md`.

## § 5. Идеи владельца — на будущее, без приоритета

Зафиксировано 2026-09-13 по прямому запросу владельца — не реализуется в текущей пачке, просто чтобы не забыть.

### 5.1. Развёрнутые описания в справочнике (не только имя + ссылка на страницу книги)

Сейчас почти все каталоги (`RacialAbility`, боевые фиты, техники/Spellsongs, Evocations, Aspects/Stratagems/Essence Weavings/School Secrets, Work Skills, заклинания) хранят только имя, уровень/круг и классификационные метаданные — текста эффекта нет нигде в приложении, только ссылка на страницу книги. Причина зафиксирована в комментариях кода (`combat-feats.ts`, `races.ts`) и в `docs/legal.md`: исследовательские доки с полным текстом есть только на русском, а приложение двуязычно — расписать эффект пришлось бы на оба языка по каждой из тысяч записей (672 заклинания, ~150 фитов, 64 Secret, 81 Work Skill и т.д.).

**Это решение по архитектуре данных, не мелкая доработка экрана.** `docs/legal.md` также напоминает: пока репозиторий приватный, встраивать дословный текст правил можно свободно, но если когда-нибудь встанет вопрос публикации (см. §2 «Приватность GitHub Pages») — печатать текст правил verbatim станет юридически рискованно, придётся перефразировать.

Открыто для владельца: с каких каталогов начать, насколько подробно (краткая выжимка своими словами vs дословный текст книги), на каком языке (RU-only текст эффекта при двуязычном интерфейсе, или переводить оба).

### 5.2. Готовые персонажи для быстрого старта

После того как разбор всех рас и классов будет закрыт (сейчас закрыт почти полностью, см. § 1) — набор заготовленных персонажей (по одному-два на класс/архетип), чтобы сесть играть без создания персонажа с нуля.

### 5.3. Пошаговый гид по созданию персонажа для новичков

Отдельный раздел приложения с пошаговым описанием процесса создания персонажа (что такое раса/предыстория/коррекция и т.д.), ориентированный на игрока, который не хочет читать правила по книге.

### 5.4. Игровое поле (боевая карта) с токенами

Отдельная будущая подсистема, ортогональная листу персонажа: карта боя с токенами игроков и монстров, загрузка изображений карты и токенов, сохранение состояния поля между сессиями. Потребует отдельного проектирования (canvas/рендеринг, хранилище изображений — с учётом квоты localStorage, уже упомянутой в граблях `state.md` — и то, как это соотносится с приватностью проекта из `docs/legal.md`, если карты/токены когда-либо станут общими для группы, а не только локальными).

### 5.5. Компактная/многоколоночная вёрстка листа персонажа

Сейчас лист — один длинный скролл (`docs/design.md`, решение от 2026-08-04, мотивированное упрощением печати: все секции уже в DOM, без отдельной логики раскладки). Владелец хочет более компактный вид без сплошного скролла. Переоткрывает вопрос, который уже закрывался осознанно («Компактный/расширенный вид... не делались, при одном скролле пока не нужны»). Вероятный путь — чисто CSS-раскладка (grid/flex-колонки на экране, с откатом на одну колонку в `@media print`), не трогая порядок секций в DOM, — но требует отдельной проверки в браузере и на печати, когда до этого дойдёт очередь.

## Что считать «сделано»

Критерий не менялся с начала разработки и проверяется перед каждым коммитом:

1. `npm test`, `npx tsc -b`, `npx oxlint`, `npm run build` — зелёные.
2. Новые данные закрыты тестом на счётчики и уникальность id, иначе следующая правка тихо потеряет строку.
3. Новые поля схемы — через `.default(...)`: сохранённые персонажи должны читаться.
4. UI проверен **в реальном браузере**, а не только в jsdom, и отдельно — **на печати**. Список того, чего jsdom не видит в принципе, — в «граблях» `state.md`.
5. Разбор книги записан в `docs/sheet-content/`, а не только в код.
